# console/: PB Console

A local admin console and health checker for the whole Project Board: the Pi, the LEDs, the wall kiosk, the live app and Supabase. It runs on the laptop, in the browser, and reaches the Pi over Tailscale with the laptop's SSH key. Claude Code is for writing features; the console is for running, tuning, fixing and (in later phases) shipping. The plan for every phase is in `docs/console-plan.md`.

## Start it (Git Bash, at the repo root)

```
bash console/start.sh
```

It makes a new random session token, starts the backend on `127.0.0.1:8765` and opens `http://127.0.0.1:8765/#c=<code>` in the default browser: a **one-time code**, which the page swaps for the token (`POST /api/session`) and takes out of the address bar. The code works once, for two minutes, so the token itself is never in a URL, the browser's command line, its history or the terminal (review CON-09, 15 Nov 2026). The tab keeps the token until it's closed. **Another tab, or a tab that says it has no session:** run `bash console/start.sh` (or the desktop icon) again: a console already running just opens a new tab with a fresh code. **Ctrl+C** in Git Bash stops it. A tab left open from an earlier launch stops working (its token is old): start again and use the new tab.

**From the desktop:** `python console/desktop_shortcut.py` (once) puts a **PB Console** icon on the Windows desktop (`console/pb-console.ico`). Double-clicking it opens a Git Bash window running `bash console/start.sh`; closing that window (or Ctrl+C in it) stops the console. Run the script again if the repo moves.

Needs: Python 3 (the standard library only; Pillow only for the desktop icon), Git Bash's `ssh`, and `ssh pi@projectboard` working without a password (it does: the laptop's key). Optional settings go in `console/.env.local` (gitignored): copy `console/.env.local.example`.

**One-time on the Pi:** the Restart buttons, day/night (force, stay on) and the screen buttons use `pb-console-helper`, which a deploy installs (`bash pi/deploy.sh`; no password: `pb-install`, `pi/README.md` → Deploying). Until then the page says so and those buttons fail; everything else works.

## What it does

**The layout (Ross, 10 Nov 2026):** a sidebar of four: **Home · Holds · Activity · ⚙ Advanced**, plus **Runbook**, which appears only while the Pi isn't answering. Each has a status dot where it has one. **Ctrl+K** (or `/`, except on Holds) opens a palette that goes anywhere (Advanced's sections too) or runs a quick action (LEDs, patterns, night, end the stay-on override, screen, restarts, reboot, back up now), always through the same confirm. Release, Circuit tracks and Power were removed on 10 Nov 2026 (Claude Code ships; the Pi doesn't light tracks; the relays aren't fitted): their code is in git history.

- **Home** (`static/dash.js`): one page you drill into. The **status line** on top (what needs a look, as chips you can click or dismiss; the Pi's uptime, casts in 24 h, the last cast, day or night; a Runbook button when the Pi is offline). Then the tiles; a click opens the **drawer** with the detail and every line behind it:
  - **Board:** the webcam with what the LEDs show and day/night over it, and the controls: LEDs (idle now, off, default), idle pattern, brightness, **Stay on until HH:MM** (and End override), Night (Auto, or Force night/day for tests: `NIGHT_FORCE`), the wall screen, and **Light a problem** (a real `cast_problem`, plain or mirrored, then when the listener received and lit it, from its journal). Its drawer: what the board is doing in full and the last casts. Patterns, LEDs off and brightness last until the listener restarts (`pb-idle`); the permanent ones are in `config.env`.
  - **Health:** temperature (gauge), **power** (under-voltage now, or how often this week), Wi-Fi, disk, each with a 7-day line; services (a Restart beside any that's down), the live site and Supabase, and self-healing (fixes in 24 h, journal errors). Its drawer: **7-day charts** of temperature (each 5-minute reading and the highest in it, 70 °C and 80 °C marked), power (under-voltage red, throttling amber), Wi-Fi signal and disk; every service with Restart, Restart the wall screen, Reboot the Pi; and every line of the checks. The history is the Pi's own (`pb-healthlog`, below): the laptop only reads it (`probe.py healthlog`, `GET /api/health-history`, cached 4 minutes). The Pi 4 can't measure its supply voltage; "under-voltage" is its firmware's flag for a drop below about 4.63 V, checked every 15 s.
  - **Activity · 7 days:** casts per day and the three most cast; Activity has the rest.
  - **Opening hours:** day or night and the next switch, the week's hours (today in bold). Its drawer **edits the hours** (per day from, to, or Closed; a "to" of 00:00 is midnight; London time; re-read within 10 s, no restart), written like any config change. Amber while anything overrides the hours: a stay-on override, `NIGHT_FORCE` or `NIGHT_MODE=off` (`tiles.py` `schedule_tile`).
  - **Recent actions:** the last six; **Clear** hides them here (Advanced → Audit keeps them all).
  - **Board snapshot** (12 Nov 2026, `tiles.snapshot_tile`, from the laptop checks): amber while the app's bundled board (`app/hold_map.json` `__meta`) is behind the live board version, i.e. a publish (phone, console or Trace Holds) hasn't been snapshotted; its drawer goes to Holds → Ship the snapshot.
  - **Backups** have no tile: they show in the status line only when the last try failed or the newest good backup is more than 8 days old (`tiles.backup_tile`), with Back up now in the drawer.
  - **Dismiss:** the x beside a chip (or Dismiss all, Dismiss in the drawer, or Ctrl+K) hides that warning until it changes: each check carries a `sig` from `tiles.py` (its level and value; for journal errors the newest error's time, for self-healing the last action), so a new error or a worse level brings it back; "N dismissed · show again" undoes it. Kept in this browser's localStorage.
  - The checks behind it, every 30 s (**Refresh** probes at once): the Pi online (uptime, last boot, the boot check line), temperature, throttling and under-voltage, disk and memory, Wi-Fi (signal, connection, rescue hotspot), each service (listener, kiosk, Wi-Fi watchdog, webcam) and the timers, the listener (joined, what the LEDs show, fps, last cast), the live site and its `sw.js` CACHE against the stamp `build.sh --stamp origin/main` gives, Supabase (REST, and a Realtime join of `board:HangoutPortland` every 5 minutes), the self-healing actions (pb-health, watchdog restarts, pb-netwatch) and the journal's errors in 24 h by source. The Pi side is `console/probe.py`, sent over ssh and run as `pi`: it reads, never writes.
- **Holds** (10 Nov 2026, `docs/console-plan.md` phase 17): the live board's outlines, footholds and foothold pairs, laptop-first. Pick any hold or foothold from the list (`/` and its name then Enter, ↑/↓ or J/K to walk the list, "Most points first" puts the over-traced on top; each row shows its point count, amber from 30, red from 60) or on the board (wheel to zoom, drag to move). **Clear and draw** (C) a fresh outline point by point (Backspace takes one back, Enter or the first point finishes, Esc stops), drag, Shift+click or double-click points, **Simplify**, **Revert**; **New foothold** (N; named FTn and paired by the board's reflection as in the app), **Pair with…** (P), **Unpair**, **Delete foothold** (not while a problem uses it). Undo/Redo; the draft stays in this browser. **Publish** lists every change, then calls `admin_publish_board()` as the super admin over direct Postgres (the same RPC and checks as the phone's Edit holds; refused if the board was published since the page loaded, by the console under the row lock and again by the server, which takes the expected version since db/45; the corners are left as they are; a new foothold's number is above `board_config.foot_id_max`, never an old id); **Undo the last publish**; **Ship the snapshot** (pulls main first if GitHub is ahead, then `snapshot_board.py`, `check_holds.py`, the build check, a commit of the four snapshot files, push main, then the Pi's automatic deploy). Turning a hold and new photos stay in the app's Board Setup (they upload an image, which the console can't).
- **Activity:** a dashboard that fits the window (no scrolling at 1366×768 or 1920×1080), built from the approved prototype `tools/activity-dashboard-prototype.html` (fake data; kept as the design reference). The last cast; 7 days / 30 days / All (all end today), by day or week; five tiles (casts, active members, new accounts, ticks, busiest day) against the previous equal period; a main chart (casts stacked by wall, phone and console, or members, ticks, new accounts); a weekday × hour heatmap (08–22); who's using it (top members with casts and ticks, a "new" badge for accounts under a week old, and guests); what they're climbing (problems cast, circuits, most ticked, with grades); how it's cast (where from, members and guests, mirrored share, circuit runs and how many reached the top, casts tried outside the opening hours). Clicking a bar, a heatmap square or label, a member, a climb or a source filters every other panel (the chips row lists the filters; click again to clear); bars, squares and rows work from the keyboard too. **Log** lists every cast, circuit run and circuit lit on the wall in the range, newest first. Definitions: a cast is a problem cast or a circuit run start received in the daytime (not a circuit lit on the wall, not the cast-test names; console test casts count); casts ignored at night are counted only as tried outside the hours; a member is a cast with a nickname or a tick, a guest a cast with none; a circuit reached the top when its run ended "finished". All dates and hours are UK time. **Data:** the console keeps its own cast history in `console/data/activity-history.json` (gitignored), read from the Pi's journal on each refresh (`probe.py history`, the last hour again, merged without repeats), because the journal expires after a month; members' nicknames (matched from the private cast log, db/34: a circuit by its run token, a problem by name within 2 minutes), ticks and accounts are read live over direct Postgres with `db/.env` (`console/castlog.py`, read-only). Without `db/.env` the page says so and shows casts as member or guest only (`console/activity_history.py`, `static/activity.js`, `GET /api/activity-history`).
- **⚙ Advanced:** one page of closed sections; opening one loads it (and a link to, say, Logs opens Advanced there).
  - **Logs:** the journal for one unit or tag (or the kernel, all errors, everything), a time range (`-1h`, `2 hours ago`, `today`, `2026-10-28 14:00`), a line count, a filter (case-insensitive text) and **Follow**; also `pb-netlog`'s report (`/var/log/pb-netlog.txt`), pb-netwatch's own log (`/var/log/pb-netwatch.log`) and its once-per-boot copy on the SD card (`netwatch-card`; since 15 Nov 2026 nothing writes the FAT boot partition regularly).
  - **Config:** the Pi's `config.env` as a form (the opening hours are on Home), every key checked (the same checks as the helper on the Pi); Apply shows the change first; the Pi backs up the old file, restarts the listener only when a key it reads at start changed, and the laptop's `pi/config.env` follows. Earlier copies (the last 30) with what putting each back would change. When the two copies differ: keep the Pi's or keep the laptop's.
  - **Deploy:** the Pi updates itself from main (`autodeploy.py`, below; this shows its last result). By hand: `bash pi/deploy.sh` from the page (the same deploy lock and fingerprint record as autodeploy, and refused while the laptop's and the Pi's `config.env` differ: keep one in Config first), a dry run, and a drift check: every file `install.sh` places, hashed on the Pi against the repo (both sudoers rules too, through the helper); files on the Pi the repo doesn't have, with a button to pull them in; NetworkManager profiles pulled with every password line stripped on the Pi.
  - **LED map:** start and stop `pb-ledmap` and use it beside the webcam; keep exported results in `console/data/ledmap/`. Only needed after rewiring.
  - **Tests:** the R8 acceptance checklist with a button per step and pass/fail notes (`console/data/acceptance.json`), and "check a night": the closing and the next opening switches from the journal, for the night that began on a date or covers it (a closed Friday is Thursday's night; `mode.py --night`).
  - **Backups:** **weekly by themselves** (10 Nov 2026, `console/backups.py`): the Pi's settings as a tar.gz (secrets stripped on the Pi) and **a dump of the whole database** (since 15 Nov 2026, review CON-04, Ross's decision): every table in the public schema, members' data included (profiles, ticks, favourites, circuit runs, challenge attempts, the cast log, board versions, …), found from the catalogue each time so a new table is in it without a change. It's read over `db/.env` in one `repeatable read, read only` transaction (every table from the same moment, nothing can be written), one JSON file per table (`<table>.json`, an array of rows as Postgres' `to_jsonb` gives them) plus `manifest.json` (each table's row count and columns). Each table is checked against `count(*)` in that transaction and read back from disk, so a truncated read or write fails the backup. Into `backups/<date>/db-HHMMSS/` (written as `.partial` and renamed when complete): **gitignored, refused by the pre-commit hook, on this laptop only, never committed or uploaded, not encrypted.** The newest 8 dumps are kept, older ones deleted after each good one. Not in it: the sign-ins themselves (Supabase Auth's `auth.users`) and the board images (Storage). The scheduled task that keeps the Pi up to date (`autodeploy.py`, every 10 minutes) makes one when the last good one is 7 days old (from the Pi that `.env.local`'s `PB_HOST`/`PB_SSH` name, as the console does), retrying hourly after a failure; the console does the same while it's open. State in `console/data/backups.json` (counts only, never a row). Back up now (or the Pi or the database alone) by hand; the list of what's there. **Restoring:** the last section below.
  - **Audit:** every action from `console/audit.log` (gitignored): time, action, result, how long.
- **Runbook** (only while the Pi isn't answering): the rescue-hotspot steps and the key sections of `pi/README.md`, readable when the Pi isn't.

Not built yet: the rest of **Data** (phase 13: benchmarks, hand-hold mirror partners, relabels). Ross chose direct Postgres through `db/.env` (28 Oct 2026); Holds uses it; `docs/console-plan.md`.

## Safety

- **Confirm** before anything that restarts, reboots, deploys, ships the board snapshot, casts or writes config (one confirm each). The dialog says exactly what happens and shows the command or the diff.
- **Board busy** (`probe.py busy`, 10 Nov 2026): before a stop, restart, reboot, deploy, Light a problem, mapping session or acceptance step it asks the Pi whether anyone used the board in the last 15 minutes in opening hours (casts, circuits, circuit views, live LEDs while setting, a running circuit, a wall-screen touch from `pb-touchwatch`; never busy outside the hours, always busy while `pb-ledmap` runs) and shows what it found. The automatic Pi deploy uses the same check. Going ahead anyway takes a second step: after the confirm, a separate **Go ahead anyway** dialog (review CON-08); the server refuses a busy action the page didn't send that way.
- **A closed tab doesn't cut an action in half** (review CON-03): a local or Pi command is stopped, but a Python action (a publish, an undo, Ship the snapshot, a backup) only stops at a safe point before its irreversible step (the RPC; the commit); once that has happened it finishes (a snapshot commit is always pushed), and the audit records what the action itself returned.
- **One action at a time:** a second one is refused while another runs (logs don't count).
- **config.env stays in step:** Force and Config (the opening hours among it) write `/etc/projectboard/config.env` on the Pi (through the helper, which backs up the old copy to `/var/lib/projectboard/config-backups/`) and then copy it to the laptop's `pi/config.env`, so the next `bash pi/deploy.sh` doesn't put the old values back. If the two copies already differ, the console refuses and shows the diff.
- **pb-ledmap and pb-listener** never drive the strip together: the units' `Conflicts=` does it, and the console doesn't start either around it.
- Migrations are never applied by the console. Its only database writes are the board's holds (Holds: `admin_publish_board()` / `admin_undo_board()` as the super admin), each confirmed, one transaction; once it has committed (never before: review CON-07), the rows it replaced go to `console/data/undo/` as a record. Every other database read is one `begin read only` transaction (castlog.py, the backup), never a session setting (CON-06).
- **Ship the snapshot pushes its own commit and nothing else** (review CON-02): it refuses while main has local commits not on GitHub or the repo has changes outside the four snapshot files (so the build gate checks exactly what's pushed), and pushes only when HEAD is exactly one snapshot commit ahead of `origin/main`. A ship whose push never happened is pushed by the next Ship the snapshot.
- **Pulling a Pi-only file** (Deploy → drift) takes only a normal path straight inside `/usr/local/bin`, `/usr/local/sbin` or `/etc/systemd/system` that the drift check lists when the pull runs (read again from the Pi), never into a file git tracks or one already there, and refuses a password-like line, a private-key block or a long token-like line (review CON-01).

## Security

- The backend binds **127.0.0.1 only**, refuses to share its port, and sends a strict CSP, no CORS headers.
- **Every `/api/` request needs this launch's token** in `X-PB-Token` (compared in constant time), except `POST /api/session`, which swaps a one-time code for it (same Origin, same-origin fetch, JSON; a code works once, for two minutes). The token never goes in a URL: the opened address carries only the code (review CON-09). The static page (`/`, `/static/*`, `/tokens.css`) needs no token: it holds no data.
- The LED mapping tool (served by the Pi over plain HTTP, Tailscale only) is framed with `sandbox` (scripts, forms, downloads; no top navigation, no pop-ups) (review CON-10).
- The **Host** must be `127.0.0.1:<port>` or `localhost:<port>` (stops DNS rebinding); an **Origin**, when sent, must be the console's own, and a POST must send one; on `/api/`, **Sec-Fetch-Site** must be `same-origin` or `none`. Only GET and POST; every POST is JSON; everything that changes something is a POST.
- The page never sends a command: only an action name and its arguments, which `console/actions.py` checks against fixed lists and builds into a fixed command (and `pb-console-helper` checks them again on the Pi).
- **Root on the Pi:** only `/usr/local/sbin/pb-console-helper` runs without a password, through `/etc/sudoers.d/pb-console`. It takes a fixed list of commands (units, reboot, night, stay-on, screen, config writes with every key checked, the mapping tool, hashes, NetworkManager export and backup with secrets stripped, the acceptance-test steps) and refuses everything else: `pi/README.md` → PB Console. Deploys have their own rule, `/etc/sudoers.d/pb-deploy`: `pi` may run `/usr/local/sbin/pb-install` (root-owned, no arguments), which installs only a bundle signed by the laptop's key and runs `install.sh` from a root-only folder (15 Nov 2026; `pi/README.md` → Deploying).
- **Acting as the super admin** (Holds): a publish sets the transaction's JWT claims to the one `is_super_admin` profile and the role to `authenticated` before calling the RPC, so the database's own checks (`is_super_admin()`, RLS, the RPC's validation) decide, never the console. That power comes from `db/.env` on this laptop; nothing in the page or the repo carries it.
- No sign-in: the boundary is the laptop's Windows login, the SSH key and Tailscale. Serving it to a phone would use Tailscale identity, not a login page (`docs/console-plan.md`).

## Restoring from a backup (by hand)

Nothing restores automatically, and nothing should: a restore overwrites live data, so it's a deliberate, one-off job (with Claude Code, through `db/apply.py`, dry run first). What a dump is and isn't:

- `backups/<date>/db-HHMMSS/manifest.json` lists every table, its row count and its columns (names and types) at the moment of the dump. Each `<table>.json` is a JSON array of that table's rows, one object per row, keyed by column name, exactly as `to_jsonb(row)` gave it.
- **The schema isn't in it.** The tables, policies and functions come from the numbered scripts in `db/` (and `db/board_rpcs_live.sql` for the live board RPCs). Restore into a database that has them.
- **The sign-ins aren't in it.** `profiles` rows point at Supabase Auth's `auth.users`, which the dump doesn't hold (nor the PIN hashes). After losing the whole project, members would need new accounts; the rest of their data comes back only where their `auth.users` row still exists (or is recreated with the same id). Supabase's own backups are the copy of Auth.
- **One table, rows lost or damaged:** in one transaction, insert the dump's rows that are missing: `insert into public.<table> select * from jsonb_populate_recordset(null::public.<table>, <the file's JSON>::jsonb) on conflict do nothing;` (pass the JSON as a script's parameter rather than pasting it). Check the count against `manifest.json`.
- **Several tables:** parents before children (`profiles`, `problems`, `circuits`, `challenges`, `holds` and `board_config` before `ticks`, `likes`, `circuit_likes`, `circuit_logs`, `challenge_attempts`, `cast_log`), or `set local session_replication_role = replica` inside the transaction to hold back the foreign-key checks and triggers while loading (then check by hand). Triggers that stamp values (`challenge_attempts`' totals, the board copies in `board_config`) would otherwise recompute them.
- **Members' data in a dump is personal data:** while checking, look at counts only; never paste rows into a chat, an issue or the repo, and delete a copy made elsewhere once the restore is done. A member who deleted their account stays in older dumps for up to 8 weeks (`app/privacy.html` says so); after a restore, delete again any account deleted since that dump.
